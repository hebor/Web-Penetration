# PHP原生开发

原生开发指的是仅通过PHP本身编写代码，一个完整的Web站点需要通过前端实现页面美化、通过后端实现业务逻辑，对于网络安全人员而言，没有太大必要将精力过多的花费在研究页面美化上。一般的业务流量路径可以简单概括为：客户端 -> 服务端 -> 数据库，服务端可以为客户端提供美观、易懂的操作界面，数据库可以用于存储用户提交的数据

### 1.3 数据库操作

PHP函数：连接、选择、执行、结果、关闭

- mysqli_connect()：打开一个新的连接到MySQL
- mysqli_select_db()：更改连接的默认数据库
- mysqli_query()：执行某个针对数据库的查询
- mysqli_fetch_row()：从结果集中取得一行，并作为枚举数组返回
- mysqli_close()：关闭打开的数据库连接

#### 1.3.1 测试数据库连接

### 1.8 小结

留言板功能实现完成后，通过浏览器的开发者工具可以看到PHP代码是看不到的，只能看到PHP代码执行逻辑后的结果，所以在PHP代码中直接写`echo("<script>alert('删除成功')</script>");`，到达浏览器后就只能看到`<script>alert('删除成功')</script>`，因此浏览器会将这一段视作JavaScript代码来执行，而非输出文本

整个留言板功能对于用户而言体验最明显的地方实际上来自第三方插件，用户所有的内容提交都是通过编辑器实现的，那么用户提交的内容是否安全实际上是由编辑器负责检测，而编辑器本身的代码又不是自己写的，那么编辑器是否具备对内容的安全检测功能，全都取自于第三方插件的开发者是否在代码里写了安全检测逻辑，有就是有、没有就是没有，因此也才会产生所谓的第三方组件安全、第三方框架安全等。本质上就是你开发的程序引用了别人的代码，那么别人的代码里是否具备安全检测逻辑不是你可以控制的

对于自己写的代码，可以通过`gbook-admin.php`文件直接访问到后台数据并具备删除权限，说明不具备身份验证功能或身份验证逻辑不严谨

### 2.1 cookie

cookie是服务端为了辨别用户身份、进行会话管理而发送到用户本地终端上的一小段文本信息数据，它的核心作用是为了解决HTTP协议无状态的问题。用户本地终端会存储cookie，向同一服务端再次发起请求时会携带cookie，服务端可以通过cookie来判断多个请求是否来自同一个用户终端，以此实现保持用户的登录状态等功能。

![cookie身份验证模块-1](../image/Part_3/cookie身份验证模块-1.png)

cookie的运行原理：

1. 客户端向服务器发送HTTP请求。
2. 服务器检查请求头中是否包含cookie信息。
3. 如果请求头中包含cookie信息，则服务器使用该cookie来识别客户端，否则服务器将生成一个新的cookie。
4. 服务器在响应头中设置cookie信息并将其发送回客户端
5. 客户端接收响应并将cookie保存在本地。
6. 当客户端发送下一次HTTP请求时，它会将cookie信息附加到请求头中。
7. 服务器收到请求并检査cookie的有效性。

如果cookie有效，则服务器响应请求。否则，服务器可能会要求客户端重新登录

      * 4、错误的账号密码进行提示
      * 5、跳转到成功登录的首页
      */
      
    include "../config.php";
    
    //1、接收输入的账号密码
    $user=$_POST['username'];
    $pass=$_POST['password'];
    
    //2、判断账号密码的正确性
    $sql = "select * from user where username='$user' and password='$pass';";    //定义SQL语句
    $data = mysqli_query($connect, $sql);    //返回SQL查询的结果
    
    if ($_SERVER["REQUEST_METHOD"] == "POST") {    //这个最外层的判断，是为了避免首次访问到admin-cookie.php页面时，直接触发“登陆失败”的弹窗。用户没有通过“POST”提交表单信息时，就不会触发登陆是否成功的判断
        //3、正确后生成cookie进行保存
        if (mysqli_num_rows($data) > 0) {        //当SQL查询结果的行数不为0则判断账号密码正确
            $expire = time() + 60 * 60 * 24 * 30;    //设置过期时间为1个月，秒钟*分钟*小时*天数=30天超时
            setcookie('username', $user, $expire, '/');    //‘username’表示cookie的名称；$user表示cookie的值；$expire表示cookie的过期时间；'/'表示cookie的有效路径，/表示整个网站下都可以访问这个cookie
            setcookie('password', $pass, $expire, '/');
    
            //echo('<script>alert("登录成功")</script>');    //登陆成功后会自动跳转到index-cookie.php文件，所以是否需要登陆成功提示就不再重要
            //5、跳转到成功登录的首页
            header('Location: index-cookie.php');    //用户登陆成功后自动跳转到index-cookie.php文件
        } else {
            //4、错误的账号密码进行提示
            echo('<script>alert("登录失败")</script>');
        }
    }
    ?>
    ```

### 2.2 session

session与cookie都被用于“保持用户登陆状态”这一共同目标，只不过两者的存储位置、安全性、适用场景都不同，但大多数情况下session需要结合cookie使用，session的本体数据存储在服务端，但session_id仍需要通过cookie传递到客户端，这种情况下一旦禁用cookie，session也会一同失效，除非手动将session_id拼接到URL后面，但这种方式对session的安全性而言是毁灭性打击，且还会导致用户体验变差

![session身份验证模块-1](../image/Part_3/session身份验证模块-1.png)

session运行原理：

1. 客户端向服务器发送HTTP请求

2. 服务器为客户端生成一个唯一的session ID，并将其存储在服务器端的存储器中（如文件、数据库等）。 

3. 服务器将生成的session ID作为一个cookie发送给客户端。 

4. 客户端将session ID保存为一个cookie，通常是在本地浏览器中存储。 

5. 当客户端在发送下一次HTTP请求时，它会将该cookie信息附加到请求头中，以便服务器可以通过该session ID来识别客户端。 

6. 服务器使用session ID来检索存储在服务器端存储器中的与该客户端相关的session数据，从而在客户端和服务器之间共享数据。

#### 2.2.1 cookie与session的区别

cookie和session都是用来在Web应用中跟踪用户状态的机制，两者各有优劣，选择使用那种方式，取决于具体的应用场景和需求。一般来说，如果需要存储敏感信息或者数据较大，建议使用session；如果只需要存储少量的数据，并且需要在客户端进行访问，可以选择使用cookie

| 区别         | cookie                                                       | session                                                 |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------- |
| 存储位置不同 | cookie存储在客户端浏览器                                     | session存储在服务端                                     |
| 安全性不同   | cookie存储在客户端，可能被攻击者利用窃取信息                 | session存储在服务端，更加安全                           |
| 存储容量不同 | cookie存储容量有限，一般为4KB                                | session存储容量理论上没有限制，取决于服务端的硬件和配置 |
| 生命周期不同 | cookie能够设置过期时间，即便关闭浏览器或重启PC，cookie仍然存在，直到过期或删除 | session默认在浏览器关闭后就过期                         |
| 访问方式不同 | cookie可以通过JavaScript访问                                 | session只能在服务端进行访问                             |
| 使用场景不同 | cookie一般用于存储小型数据，例如用户名、密码等信息           | session一般用于存储大型数据，例如购物车、登录状态等信息 |

获取cookie和获取session对于攻击者而言完全两种不同的测试流程，获取cookie时攻击者的目标主要是用户本身、获取session时攻击者的目标是服务端。但是获取session本身似乎就与攻击的目标相悖，获取session意味着攻击目标是服务端，攻击者能够获取session文件的时候，说明已经拿到服务端的部分权限了，此时似乎无须再纠结某个用户的登录权限

从session的生命周期来看，一旦客户端与服务端会话终止，session就会失效，攻击者需要在客户端与服务端保持正常会话的期间，获取到客户端与服务端的session id，以这个session id与服务端建立连接，会话才会成功。从安全性方面来看，session的安全性更高，但同样的，session对服务端的性能损耗更大，特别是在大量用户访问的场景下，每个浏览器在访问服务端时都会生成一个新的session_id，所有用户的session id都需要保存在服务端，这对服务端来说就是成本

### 2.3 token

在Web应用程序中，是否采用token机制的主要差异在于身份验证和安全性，如果说cookie、session还以身份校验、会话状态功能为共同目标，那么token可以说是以数据唯一性为目标

| 差异     | 使用token                                                    | 未使用token                                                  |
| -------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 身份验证 | 用户在登录成功后会收到一个token，这个token可以在每次请求时发送给服务器进行身份验证 | 一般会使用session机制来保存用户登录状态，服务器会在用户登录成功后创建一个session，之后的每个请求都需要在HTTP头中附带这个session ID，以便服务器能够验证用户身份 |
| 安全性   | 服务器上不会存储用户的登录状态，只需要存储token即可，因此，即使token被盗取，黑客也无法获得用户的密码或者其他敏感信息 | 一般会在服务器上存储用户的登录状态，因此如果服务器被黑客攻击，黑客可能会获得用户的敏感信息 |
| 跨域访问 | 在跨域访问时，可以使用HTTP头中的Authorization字段来传递token信息，方便实现跨域访问 | 在跨域访问时，需使用cookie或session来传递用户身份信息，比较麻烦 |


token机制可以提高Web应用程序的安全性，并且方便实现跨域访问。然而，token机制本身也需要开发者自己来实现身份验证和token的生成和验证，代码逻辑相对来说比较复杂。使用session机制则相对简单，但是安全性相对较低。因此，具体采用哪种机制，需要根据实际情况进行权衡和选择。

token（令牌）在计算机安全和 Web 开发中，指的是一段经过加密签名的字符串，用于代表用户的身份或权限。它最核心的特点是“自包含”（Self-contained），与session_id只是一个指向服务器数据的“索引”不同，token 本身通常就包含了用户的关键信息（如用户 ID、角色、过期时间等），并且经过了数字签名，防止被篡改

token最著名的实现是JWT，一个典型的JWT token由三部分组成，用点号 `.` 连接：

1. Header（头部）：声明类型和加密算法。
2. Payload（负载）：存放实际数据（如 `user_id`, `exp` 过期时间）。
3. Signature（签名）：服务器用密钥对前两部分进行签名，用于验证 Token 的真伪。

- *示例*：`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c`

token本身就是一串加密的随机字符串，每一个登陆请求都是唯一的token，一旦token值异常，请求就会被视作垃圾请求。这种机制导致非常多的漏洞受到影响，受到影响最明显的就是暴力破解漏洞，实现暴力破解需要一直变更账号密码，但无法变更token，因为攻击者无法预知到下一个token值

#### 2.3.1 token示例

```
目录树：

├── admin/
│   ├── admin-cookie.php
│   ├── index-cookie.php
│   ├── logout-cookie.php
│   ├── admin-session.php

token的生成没有固定方式，由开发者主观决策选择使用生成随机字符串的加密算法，或开发者自己手搓随机字符串。

1. 编辑`admin-token.php`文件

   `admin-token.php`文件中的HTML代码均复用`admin-cookie.php`文件的HTML代码，但`admin-token.php`文件的表单部分需要单独进行修改

   ```php
   <?php
   //生成token并将其存储在session中
   session_start();
   $token = bin2hex(random_bytes(16));    //random_bytes()用于生成16个字节的随机二进制数据、bin2hex()用于将二进制数据转换为十六进制字符串表示
   //将token保存到session中
   $_SESSION['token'] = $token;
   //将token绑定到cookie中
   setcookie('token', $token, time()+3600, '/');
   ?>
   
   <!DOCTYPE html>
   <html lang="zh">
   <head...>    <!--头部区域的CSS代码均被隐藏-->
   <body>
   
   <div class="login-container">
       <h2>登录</h2>
       <!--将表单提交的数据先转发到token-check.php，对token进行校验后再进行下一步动作-->
       <form action="token-check.php" method="post">
           <!--在表单中新增隐藏属性，用于每次用户登陆时同步提交token值，这一段在代码逻辑中没有用到，是为了在测试时更直观的看到效果-->
           <input type="hidden" name="token" value="<?php echo($token); ?>"
   
           <input type="text" name="username" placeholder="用户名" required><br>
           <input type="password" name="password" placeholder="密码" required><br>
           <input type="submit" value="登录">
       </form>
       <!--    <div class="link">-->
       <!--        <p>还没有账号? <a href="/register">注册</a></p>-->
       <!--    </div>-->
   </div>
   
   </body>
   </html>
   ```
   
2. 编辑`token-check.php`文件

   ```php
   <?php
   session_start();
   $token = $_COOKIE['token'] ?? '';    //从cookie中取token值。当http请求中没有名为token的cookie值时，设置$token变量为空
   
   //对用户提交的表单数据进行校验，需要同时满足账号、密码、token值均正确
   if ($_POST['username'] == 'user01' && $_POST['password'] == 'password01' && $_SESSION['token'] == $token) {
       echo("login successful.");
   } else {
       echo("login failed");
   }
   ?>
   ```
